# v0.3.A — Notification UI + Runtime Permission + MemoDetail 등록 상태/취소

**날짜:** 2026-06-01
**상태:** 디자인 승인 대기
**선행:** v0.2 (`feature/v0.2-plan`, PR #5) merge 후 진행

## Goal

v0.2의 캘린더/알람 인프라 위에, 사용자가 실제로 인지·관리할 수 있는 UX layer를 얹는다. v0.2에서 의도적으로 미룬 세 항목을 한 번에 마무리.

1. 알람 발화 시 시스템 노티 표시 (현재 logcat만)
2. PreviewSheet 토글 ON 시 권한 다이얼로그 자동
3. MemoDetail에서 등록 상태 조회 + "등록 취소"

## Background

- v0.2 plan의 "의도적으로 미룬 항목" 표 항목 4개 중 3개를 처리. 나머지(prompt 튜닝, GPU backend 등)는 v0.3.B/C로 별도 spec.
- v0.2 디바이스 smoke에서 사용자 첫 인상은 "리마인더 잘 안돼" — 실제로는 `AlarmReceiver`가 발화는 했으나 UI 피드백이 없어 그렇게 느낌. v0.3.A는 이 인지 격차를 해소.

## Architecture

**범위**: v0.2 schedule 인프라 위 사용자 인지·관리 layer.

**영향 모듈:**

| 모듈 | 변경 |
|---|---|
| `:local` | `AlarmReceiver`에 `NotificationCompat` 통합. Notification channel 생성 헬퍼. |
| `:usecase` | `UnscheduleNoteUseCase` 신설 (interface + impl + Hilt binding). |
| `:feature_capture` | `SchedulePermissionState` 컴포저블 헬퍼. PreviewSheet 토글에서 권한 launcher 호출. 거부 시 설명 다이얼로그. |
| `:feature_memo` | `MemoDetailScreen`에 등록 상태 chip(s) + "등록 취소" 버튼. `MemoDetailViewModel`에 `UnscheduleNoteUseCase` 주입. |
| `:app` | `MainActivity`가 알람 deep link extra(`ACTION_VIEW_NOTE` + `noteId`) 처리. `AppScene`이 deep link event를 backstack 초기화로 반영. |

**Repository 무변경** — 기존 `NoteRepository.save` + `ScheduledItemRepository.cancel*` 재사용. (`save`는 id 보존된 Note 전달 시 Room의 `@PrimaryKey(autoGenerate=true) val id: Long = 0` + upsert 패턴으로 update 동작 가정. v0.2 P1에서 이미 사용 중이므로 검증된 가정.)

**의존성** — 외부 신규 dep 없음. 권한은 native `rememberLauncherForActivityResult`, 노티는 표준 `NotificationCompat`.

## Components

### `:local` — Notification

**`NotificationChannelInitializer`** (new)
- `init(context)` — `IMPORTANCE_DEFAULT` 채널 `"reminders"` 등록. 채널 이름은 strings.xml.
- 호출 시점: `AssistantApplication.onCreate`.

**`AlarmReceiver`** (modify)
- 기존 `Log.i` 유지.
- `NotificationCompat.Builder` 추가:
  - channel `"reminders"`
  - smallIcon `R.mipmap.ic_launcher`
  - title/body는 intent extras에서 추출
  - contentIntent: `PendingIntent.getActivity(...)` → `MainActivity` action `ACTION_VIEW_NOTE`, extras `EXTRA_NOTE_ID: Long`, flags `FLAG_ACTIVITY_CLEAR_TOP | FLAG_ACTIVITY_NEW_TASK`. PendingIntent flags `FLAG_IMMUTABLE | FLAG_UPDATE_CURRENT`.
  - autoCancel = true
- 요청 코드: `alarmRequestId` 재사용.
- 표시 호출: `NotificationManagerCompat.from(context).notify(requestId, notification)`.

**Note:** `AlarmReceiver.onReceive`는 noteId를 알아야 deep link 가능 → v0.2의 `EXTRA_REQUEST_ID` 외에 `EXTRA_NOTE_ID: Long`도 schedule 시 함께 박는다. 따라서 `AlarmScheduler.schedule` 시그니처에 `noteId: Long` 파라미터 추가, `ScheduleReminderUseCase` 또한 동일 추가. `CaptureViewModel.onConfirm`에서 새 Note 저장 직후 받은 id로 schedule 재호출하거나, `SaveNoteUseCase`가 id를 반환하므로 순서를 `save → schedule(noteId=id)`로 조정.

### `:usecase` — Unschedule

**`UnscheduleNoteUseCase`** (interface + impl)
```kotlin
interface UnscheduleNoteUseCase {
    suspend operator fun invoke(noteId: Long)
}
```
- 동작:
  1. `findById(noteId)` → null이면 no-op
  2. `note.calendarEventId?.let { repo.cancelEvent(it) }` (반환값 무시 — 이미 외부 캘린더 앱에서 삭제된 경우 false여도 진행)
  3. `note.alarmRequestId?.let { repo.cancelReminder(it) }`
  4. `saveNote(note.copy(calendarEventId = null, alarmRequestId = null))`
- Hilt `@Binds` in `UseCaseModule`.

### `:feature_capture` — Permission UI

**`SchedulePermissionState`** (Composable helper)
- `rememberSchedulePermissionState(): SchedulePermissionState` — 3 launcher 묶음 hoist.
- API:
  - `requestForEvent(): Boolean` (suspend 또는 callback) — READ/WRITE_CALENDAR 묶음 요청.
  - `requestForReminder(): Boolean` — POST_NOTIFICATIONS (API 33+) + Exact alarm 검사 후 필요 시 시스템 설정 deeplink.
  - `hasEventPermission(): Boolean` / `hasReminderPermission(): Boolean`
- 영구 거부 판별: `Activity.shouldShowRequestPermissionRationale` + launcher 곧장 false 반환.
- 영구 거부 시 콜백으로 "설명 다이얼로그 노출 필요" 신호. UI 측에서 `AlertDialog` + `Intent(Settings.ACTION_APPLICATION_DETAILS_SETTINGS)` deeplink.

**PreviewSheet 변경:**
- 토글 `onCheckedChange`를 직접 받지 않고 `onScheduleToggleRequest(enabled: Boolean)` 콜백으로 위임.
- 권한 검사·요청은 PreviewSheet 호출자(`CaptureScreen`) 측 Composable에서 처리 — `SchedulePermissionState` launcher가 Composable-scope이기 때문. 검사 후 granted면 PreviewSheet에 새 toggle 상태 전달, denied면 토글 OFF 유지 + 다이얼로그 state 트리거.
- Exact alarm 권한 없으면 REMINDER 토글 ON 시 별도 dialog "Alarms & reminders 설정 필요" + deeplink.

### `:feature_memo` — MemoDetail 등록 상태/취소

**`MemoDetailScreen` 확장:**
- `Loaded` state에서 다음 정보를 노출:
  - `note.calendarEventId != null` → chip "캘린더에 등록됨" (strings.xml)
  - `note.alarmRequestId != null` → chip "알람 설정됨"
  - 둘 중 하나라도 있으면 하단에 `Button("등록 취소")` (strings.xml)
- 버튼 onClick → `viewModel.onUnschedule()` → 성공 후 토스트 "등록 취소됨" + state 자동 갱신 (StateFlow가 Note 다시 emit하도록 reload)

**`MemoDetailViewModel` 확장:**
- ctor에 `UnscheduleNoteUseCase` 추가 (AssistedInject 그대로).
- `fun onUnschedule()`: `viewModelScope.launch { useCase(noteId); load() }`.
- AssistedFactory 시그니처 무변경.

### `:app` — Deep link

**`MainActivity`:**
- `onCreate`/`onNewIntent`에서 `handleIntent(intent)` 호출.
- `handleIntent`: action == `ACTION_VIEW_NOTE` && `noteId >= 0` → `MainViewModel.onDeepLink(noteId)`.

**`MainViewModel`** (이미 있다면 확장, 없다면 신설):
- `private val _deepLink = MutableSharedFlow<Long>()`
- `val deepLink: SharedFlow<Long> = _deepLink.asSharedFlow()`
- `onDeepLink(noteId)` → `_deepLink.tryEmit(noteId)`.

**`AppScene` (또는 root NavDisplay):**
- `LaunchedEffect(Unit) { vm.deepLink.collect { noteId → backstack 초기화 후 MemoSubRoute.Detail(noteId) push } }`

## Data Flow

### 1. 스케줄 등록 (PreviewSheet → 저장)
```
사용자 토글 ON (EVENT 또는 REMINDER)
  ↓ onScheduleToggleRequest(true)
  ↓ permissionState 확인
  ├ granted → 상태 변경 (scheduleEnabled = true)
  ├ 첫 거부 → 토글 OFF + 토스트 또는 silent
  └ 영구 거부 → 토글 OFF + 설명 다이얼로그 + 설정 deeplink

사용자 저장
  ↓ CaptureViewModel.onConfirm(confirmed)
  ↓ SaveNoteUseCase(Note ...) → newNoteId
  ↓ if scheduleEnabled && type==EVENT:
      ScheduleEventUseCase(input) → calendarEventId
      save 갱신 (calendarEventId 채움)
  ↓ if scheduleEnabled && type==REMINDER:
      ScheduleReminderUseCase(input, requestId, noteId=newNoteId)
      save 갱신 (alarmRequestId 채움)
```

> v0.2 구현은 schedule 후 save 단일 호출이었음. v0.3에선 `AlarmScheduler.schedule`에 `noteId`가 필요하므로 흐름이 `save → schedule → save 갱신` 순서가 된다. 또는 `SaveNoteUseCase`가 transactional하게 받을 수 있게 시그니처 조정. plan에서 깔끔하게 정리.

### 2. 알람 발화
```
AlarmManager → AlarmReceiver.onReceive(intent)
  ├ Log.i (기존 유지)
  └ NotificationCompat.Builder
     - title/body: intent extras
     - contentIntent: PendingIntent → MainActivity ACTION_VIEW_NOTE noteId
  ↓ NotificationManagerCompat.notify(requestId, notification)
```

### 3. 노티 탭 → MemoDetail
```
사용자 노티 탭
  → MainActivity.onCreate / onNewIntent
  → intent.getLongExtra(EXTRA_NOTE_ID, -1)
  → MainViewModel.onDeepLink(noteId)
  → AppScene LaunchedEffect → backstack 초기화 + MemoSubRoute.Detail(noteId) push
  → MemoDetailScreen 표시
```

### 4. 등록 취소
```
MemoDetailScreen "등록 취소" 버튼
  → MemoDetailViewModel.onUnschedule()
  → UnscheduleNoteUseCase(noteId)
     → findById
     → cancelEvent / cancelReminder
     → saveNote(note.copy(calendarEventId=null, alarmRequestId=null))
  → load() 재호출
  → state.Loaded.note에 chip 사라짐
  → 토스트 "등록 취소됨" (UI 트리거는 Effect로)
```

## Permissions

| 권한 | API | 처리 |
|---|---|---|
| `POST_NOTIFICATIONS` | 33+ | `ActivityResultContracts.RequestPermission` |
| `READ_CALENDAR` + `WRITE_CALENDAR` | all | `RequestMultiplePermissions` 한 묶음 |
| `SCHEDULE_EXACT_ALARM` | 31+ | runtime grant 불가. `Intent(ACTION_REQUEST_SCHEDULE_EXACT_ALARM)` 시스템 설정 이동 |
| `USE_EXACT_ALARM` | 33+ | manifest 선언만 (자동 grant) |

**영구 거부 판별**: `shouldShowRequestPermissionRationale = false` AND launcher 콜백이 `granted=false`로 즉시 반환되면 영구 거부로 판단. 설명 다이얼로그 + 앱 설정 deeplink.

**구현**: `SchedulePermissionState`가 3 launcher 보유 + Activity 참조로 rationale 검사. `:feature_capture` 내부 헬퍼.

## Notification

- Channel id: `"reminders"`
- Channel name: strings.xml `notification_channel_reminders` = "리마인더"
- Channel importance: `IMPORTANCE_DEFAULT`
- Channel 생성: `AssistantApplication.onCreate` 1회 (NotificationChannelInitializer)
- Builder:
  - smallIcon: `R.mipmap.ic_launcher`
  - title: `intent.getStringExtra(EXTRA_TITLE)`
  - body: `intent.getStringExtra(EXTRA_BODY)`
  - contentIntent: deep link
  - autoCancel = true
- 표시 요청 코드: `alarmRequestId` 재사용 (중복 발화 시 자동 갱신)

## Error handling

- POST_NOTIFICATIONS 없음 + 알람 발화 → `NotificationManagerCompat.notify` silently no-op. `Log.i`로 기록 (v0.2 동작 유지).
- `cancelEvent` false 리턴 (이미 캘린더 앱에서 삭제됨) → UnscheduleNoteUseCase는 계속 진행. Note만 정리.
- Deep link intent에 `noteId < 0` → 무시. 정상 앱 시작.
- 영구 거부 후 사용자가 시스템 설정에서 권한 부여 후 복귀 → 다음 토글 ON 때 정상 granted.

### 디바이스 smoke

1. **권한 자동 요청 (grant 경로)**: 앱 fresh install → Capture → "내일 3시 회의" → PreviewSheet "캘린더 추가" 토글 ON → 시스템 권한 다이얼로그 → grant → 토글 ON 유지 → 저장 성공
2. **권한 거부 후 토글 OFF 유지**: 같은 흐름에서 첫 거부 → 토글 자동 OFF + (선택) 짧은 안내
3. **영구 거부 fallback**: 거부 한 번 더 → 다시 토글 ON 시도 → 설명 다이얼로그 표시 → "설정" 탭 → 앱 설정 화면 이동 → 권한 부여 후 복귀 → 토글 ON 정상
4. **노티 표시·탭**: REMINDER 등록 (1분 후) → 1분 대기 → 알림 영역에 title/body 노티 표시 → 탭 → MemoDetail 화면 진입
5. **등록 취소**: Memo 목록 → 등록된 항목 진입 → 칩 표시 확인 → "등록 취소" → 토스트 → 칩 사라짐 → 시스템 캘린더 앱에서 해당 이벤트 삭제 확인

## Out of Scope (v0.3.A)

| 항목 | 이유 | 다음 |
|---|---|---|
| 노티에 액션 버튼 (완료/snooze) | 별도 receiver + state 관리 필요 | v0.3.B |
| 이벤트/알람 시간 편집 (이미 등록된 Note) | Note 수정 흐름 전반에 영향 | v0.3.B 또는 v0.4 |
| 노티 아이콘 디자인 (런처 아이콘 재사용 중) | 디자인 작업 | polish |
| Snooze flow | 별도 UseCase + UI | v0.3.B |
| GPU backend / prompt 튜닝 / 이미지 입력 / 모델 변종 매칭 | v0.3.B/C 별도 spec | 후속 |
